# EduNexus enrollment and Firestore security model

- Teachers authenticate, then use `createTeacherClass` with an institution-issued one-time invitation code. The class code is generated by the backend and bound to the teacher UID.
- Teachers use `addStudentToClass` to create roster records. Roll numbers are unique within a class; student IDs and parent access codes are generated on the server.
- Student users authenticate first and then call `claimStudentEnrollment` with an existing roll number and class code. Each enrollment can be linked to one student UID.
- Parents authenticate first and then call `claimParentAccess` with the institution-issued parent code. The code is single-claim and stored only as a SHA-256 hash.
- Firestore rules deny client creation of profiles, classes, roster entries, and parent-link records. Callable functions use the Admin SDK to perform trusted provisioning.

## Required deployment steps

1. Install and build `functions/`, then deploy callable functions and Firestore rules.
2. Provision `teacherInvites/{sha256(normalizedInviteCode)}` documents with `{ active: true, claimedByUid: null }` using a trusted administrator script or console. Never expose invite hashes or use a public default invite code.
3. Update the frontend to call the callable functions and show parent access codes only once, when a roster entry is created.
4. Migrate existing records to include `teacherUid`, `studentUid`, `parentUid`, and trusted class ownership. Do not infer a parent UID from the parent code.
5. Update dashboard notice writes to include `authorId` and `classCode`, and discussion messages to include `classCode`.
6. Configure Google Authentication and authorized domains in Firebase Console.

## Callable functions

- `createTeacherClass({ displayName, teacherInviteCode })`
- `addStudentToClass({ classCode, name, rollNo })`
- `claimStudentEnrollment({ classCode, rollNo })`
- `claimParentAccess({ parentCode })`
